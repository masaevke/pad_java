# ДЗ 06. Умножение через очередь сообщений

Сервис A принимает две цифры от 0 до 9 и отправляет задачу в очередь `tasks` в RabbitMQ. Сервис B ждёт 2,5 секунды, перемножает цифры и отправляет событие `JobCompleted` в очередь `results`. Сервис A читает результат и хранит его в памяти.

## Запуск

В терминале из папки `homeworks/hw_06`:

```bash
docker compose up --build
```

## Проверка из Git Bash

Когда сервисы запустятся, отправь задачу из второго терминала:

```bash
curl -i http://localhost:8080/jobs -H 'Content-Type: application/json' -d '{"a":3,"b":7}'
```

Ответ приходит сразу со статусом HTTP 202. ID каждый раз будет новым.

```json
{"id":"efe27cb0-dce9-4f89-958c-5ca97bf42601","status":"ACCEPTED"}
```

Подставь полученный ID. Сразу после отправки статус может быть `ACCEPTED`. Примерно через 3 секунды будет `DONE` и результат.

```bash
curl http://localhost:8080/jobs/efe27cb0-dce9-4f89-958c-5ca97bf42601
```

```json
{"id":"efe27cb0-dce9-4f89-958c-5ca97bf42601","status":"DONE","result":21}
```

Обе очереди можно увидеть в [RabbitMQ Management](http://localhost:15672), раздел **Queues and Streams**. Логин и пароль — `homework`. У обработанной задачи сообщение исчезает из очереди, поэтому счётчики могут быть нулевыми.

## Почему 202 и что будет при сбое

`202 Accepted` означает, что брокер принял задачу. Умножение произойдёт позже, а результат можно узнать отдельным запросом.

Сервис B подтверждает задачу после того, как RabbitMQ принял событие с результатом. Если B упадёт до подтверждения задачи, RabbitMQ доставит её снова после запуска обработчика. Это доставка **как минимум один раз** (at-least-once). Повторное умножение даёт то же число и не меняет данные. Если B уже успел отправить результат, сервис A пропустит повторное событие, потому что задача с этим ID уже в статусе `DONE`.

После перезапуска A статусы теряются, поскольку они хранятся в памяти.

## Бонус: повторная доставка

На [первом скриншоте](demo/01-before-ack.png) видны обе очереди. В `tasks` значение `Unacked = 1`: B уже опубликовал результат, но ещё не подтвердил задачу. После принудительной остановки B задача снова доступна для доставки: [Ready = 1, Unacked = 0](demo/02-returned-to-queue.png). После перезапуска B [очередь снова пуста](demo/03-after-redelivery.png), а [в логах виден тот же ID дважды](demo/04-same-job-id.png). API возвращает `DONE` и результат `21`.

Чтобы повторить демонстрацию, в Git Bash запусти `JOB_DEMO_ACK_DELAY_MS=45000 docker compose up -d --build`. Отправь задачу из примера и открой `docker compose logs -f service-b`. Как только появится строка `result published; delaying ack`, выполни в другом терминале `docker compose kill -s SIGKILL service-b`. Проверь счётчик `Ready` в очереди `tasks`, затем запусти обработчик командой `docker compose up -d service-b` и проверь его логи. При обычном запуске пауза перед подтверждением выключена.
