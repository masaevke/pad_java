# Лекция 7. Архитектура приложения

## 1. Что такое архитектура

**Архитектура = структура приложения + решения, которые трудно менять потом.**

Структура описывает, из каких частей состоит приложение и как они связаны. Главный признак архитектурного решения — высокая стоимость его изменения в будущем.

В этой лекции рассматривается **внутренняя архитектура** приложения: один процесс, один репозиторий.

- Изменить кнопку на сайте — минуты.
- Изменить тип хранения данных, структуру проекта или контракт API — недели работы и миграции.

### Три вопроса об архитектуре

1. **«Кто кого знает?»** Какие части системы знают о существовании других и в какую сторону направлены вызовы и зависимости.
2. **«Где проходит граница?»** Какие части можно менять отдельно, не затрагивая соседние: интерфейс, логику, хранение данных.
3. **«Что случится при смене X?»** Сколько кода придётся изменить при замене базы данных, провайдера LLM или дизайна.

**Главная мысль:** задача архитектора — определять зависимости и границы частей системы и понимать последствия изменений. LLM ускоряет работу, но решение о слоях и их границах остаётся за разработчиком.

## 2. Классическая слоистая архитектура приложения

Приложение разделяют на четыре слоя. Пример из CloudAsk — обработка голоса пользователя:

```text
Браузер → Controller → Service → Repository → БД
```

| Слой | Ответственность | Пример в CloudAsk |
| --- | --- | --- |
| **Controller** | Принимает HTTP-запросы, служит точкой входа для пользователя (`@Controller`). | Принимает голос по HTTP. |
| **Service** | Выполняет бизнес-правила приложения. | Применяет правила опроса. |
| **Repository** | Отвечает за доступ к данным и их сохранение. | Сохраняет голос. |
| **БД** | Хранит данные в таблицах и файлах. | PostgreSQL, H2 или MySQL. |

### Правило: зависимости направлены вниз

**В этой схеме верхние слои знают о нижних, а нижние не знают о верхних.** Controller обращается к Service, Service — к Repository, Repository — к БД.

- Repository не должен зависеть от Controller или вызывать его.
- База данных не знает о контроллерах, а сущность (Entity) не должна знать об HTTP.
- Бизнес-правила относятся к Service, а не к HTML или коду хранения данных.

Такое разделение ограничивает последствия изменений: изменение кнопки на сайте не должно требовать правок в базе данных.

### Уточнение преподавателя: сервис нужен не для каждой операции

**Контроллер может обращаться к репозиторию напрямую, если отдельной бизнес-логики нет.** Например, для простого получения данных допустима цепочка `Controller → Repository → БД`. Создавать сервис, который только перенаправляет тот же вызов репозиторию, необязательно.

Если операция содержит бизнес-правила, вычисления или координирует несколько действий, эту логику выделяют в Service. Таким образом, схема из четырёх слоёв описывает разделение ответственности, но не требует проходить через сервис в каждом запросе. Направление зависимостей при прямом обращении к репозиторию сохраняется — сверху вниз.

**Интерфейс задаёт узкий контракт между слоями:** вызывающему коду доступны предусмотренные контрактом операции. Например, интерфейс Service может предоставлять пять методов; Repository при этом не получает ссылку на Controller и не может обращаться к нему.

**Важно:** стрелки обозначают направление зависимостей и вызовов. Результат вызова может возвращаться наверх — это не создаёт обратную зависимость.

## 3. Структура стандартного Spring Boot-приложения

На примере проекта `cloudask-backend` слои распределены по пакетам:

```text
src/
├── main/
│   ├── java/com/cloudask/
│   │   ├── config/                   — конфигурация приложения
│   │   ├── entity/                   — сущности данных
│   │   ├── repo/                     — репозитории, доступ к данным
│   │   ├── service/                  — бизнес-логика
│   │   ├── web/                      — веб-слой, контроллеры
│   │   └── CloudAskApplication.java  — точка входа
│   └── resources/
│       ├── application.yml           — настройки приложения
│       └── schema-session.sql        — SQL-скрипт схемы сессий
└── test/                            — тесты
```

В корне проекта также находятся `pom.xml` (описание Maven-проекта и зависимостей), `Dockerfile` (инструкции сборки Docker-образа), `README.md` и `.gitignore`. Каталог `target/` содержит результаты сборки Maven.

### Точка входа

```java
package com.cloudask;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class CloudAskApplication {
    public static void main(String[] args) {
        SpringApplication.run(CloudAskApplication.class, args);
    }
}
```

Метод `main` запускает приложение через `SpringApplication.run(...)`. Аннотация `@SpringBootApplication` отмечает основной конфигурационный класс Spring Boot, включает автоконфигурацию и сканирование компонентов. Размещение этого класса в корневом пакете `com.cloudask` позволяет сканировать вложенные пакеты приложения.

**Связь с архитектурой:** `web → service → repo → БД`. Пакеты `config` и `entity` дополняют эту структуру; само разбиение на папки ещё не гарантирует соблюдения границ — важны зависимости между классами.

## 4. Контроллеры в пакете `web`

В CloudAsk контроллеры собраны в `com.cloudask.web`. На экране показан `AdminController`, который управляет токенами приглашений.

### Аннотации и маршруты

```java
@RestController
@RequestMapping("/api/admin/invites")
public class AdminController {
    // ...
}
```

- `@RestController` обозначает контроллер, методы которого возвращают данные в теле HTTP-ответа.
- `@RequestMapping` задаёт общий путь для методов контроллера.
- `@GetMapping` без дополнительного пути обрабатывает `GET /api/admin/invites` — получение списка приглашений.
- `@PostMapping` обрабатывает `POST /api/admin/invites` — создание приглашения.

### Зависимости через конструктор

```java
private final InviteTokenRepository invites;
private final TokenService tokens;

public AdminController(InviteTokenRepository invites, TokenService tokens) {
    this.invites = invites;
    this.tokens = tokens;
}
```

Контроллер получает репозиторий приглашений и сервис генерации токенов через конструктор. Это внедрение зависимостей: нужные объекты передаются контроллеру извне.

### Данные ответа и обработка запросов

Для ответа используется DTO — отдельное представление данных для передачи клиенту:

```java
public record InviteDto(
    String token,
    Instant expiresAt,
    Instant usedAt,
    Long usedBy,
    Instant createdAt
) {}
```

В показанном коде у `InviteDto` также есть статический метод `of(InviteToken t)`, который преобразует сущность в DTO.

| Запрос | Что делает метод |
| --- | --- |
| `GET /api/admin/invites` | Получает приглашения через `findAllByOrderByCreatedAtDesc()`, преобразует их в DTO и возвращает список от новых к старым. |
| `POST /api/admin/invites?days=7` | Принимает срок действия, генерирует токен длиной 32 символа, создаёт и сохраняет приглашение, возвращает DTO. |

Параметр `days` читается через `@RequestParam(defaultValue = "7")`: если его нет, используется 7 дней. Допустимый диапазон — от 1 до 90 дней; иначе выбрасывается `ResponseStatusException` со статусом `400 Bad Request`. Успешный ответ создания возвращается через `ResponseEntity.ok(...)` со статусом `200 OK`.

**Наблюдение об архитектуре:** здесь Controller обращается и к Service, и напрямую к Repository. По уточнению преподавателя, прямой доступ допустим для операций без отдельной бизнес-логики — например, получения списка приглашений. Проверка срока и создание приглашения также показаны в контроллере; при усложнении этих правил их можно выделить в сервис. Само наличие зависимости от Repository не является ошибкой.

### Пример: создание приглашения администратором

Повторный показ `AdminController` иллюстрирует небольшой контроллер с двумя зависимостями: `InviteTokenRepository` и `TokenService`.

Для запроса `POST /api/admin/invites?days=7` выполняется следующая цепочка:

1. Контроллер получает `days` и проверяет диапазон 1–90.
2. `tokens.random(32)` генерирует строку токена.
3. Создаётся `InviteToken` со сроком истечения `Instant.now().plusSeconds(days * 86400L)`.
4. `invites.save(invite)` сохраняет приглашение через репозиторий.
5. `InviteDto.of(...)` преобразует сохранённую сущность в DTO, а `ResponseEntity.ok(...)` формирует HTTP-ответ.

Здесь видны разные обязанности: приём параметров и формирование ответа, правила создания приглашения, сохранение данных. По ним можно обсуждать границы между веб-слоем, сервисом и репозиторием.

## 5. Единый обработчик ошибок — `ApiErrorHandler`

Класс `ApiErrorHandler` находится в пакете `com.cloudask.web` и централизованно преобразует исключения в HTTP-ответы с понятным сообщением для клиента.

```java
@RestControllerAdvice
public class ApiErrorHandler {
    public record ErrorBody(String message) {}
    // Методы обработки исключений
}
```

- `@RestControllerAdvice` позволяет вынести общую обработку ошибок контроллеров в отдельный класс и возвращать данные в теле ответа.
- `@ExceptionHandler(...)` указывает, какое исключение обрабатывает конкретный метод.
- `ErrorBody` задаёт единый формат тела ошибки: `{"message": "Описание ошибки"}`. Фронтенд читает это сообщение через свой `ApiError`.

### Обрабатываемые исключения

| Исключение | HTTP-ответ | Сообщение |
| --- | --- | --- |
| `ResponseStatusException` | Статус берётся из исключения: `e.getStatusCode()`. | Причина из `e.getReason()`; если её нет — стандартное описание статуса. |
| `MethodArgumentNotValidException` | `400 Bad Request`. | Сообщение первой ошибки поля; если оно недоступно — «Проверьте поля формы». |
| `AuthenticationException` | `401 Unauthorized`. | «Неверный email или пароль». |

Например, ошибка срока приглашения из `AdminController` превращается в ответ со статусом `400` и телом:

```json
{"message": "Срок инвайта — от 1 до 90 дней"}
```

**Зачем нужен обработчик:** контроллеры могут выбрасывать исключения, а общий класс отвечает за формат ошибок и HTTP-статусы. По комментарию в показанном коде, до его добавления ответ приходил с пустым телом и пользователь видел только статус.

**Архитектурная роль:** преобразование исключений в HTTP-ответы относится к веб-слою. Такой обработчик не является отдельным слоем хранения или бизнес-логики. Здесь перехватываются три указанных типа исключений; наличие класса не означает, что он обрабатывает любую ошибку приложения.

## 6. Ограничение попыток входа — `RateLimitFilter`

На скриншоте показан **фильтр запросов**, связанный с защитой авторизации: `RateLimitFilter` в пакете `com.cloudask.web`.

```java
@Component
public class RateLimitFilter extends OncePerRequestFilter {
    private final RateLimiter limiter;

    private record Rule(String pathPrefix, int max, Duration window) {}
    // ...
}
```

`@Component` регистрирует класс как компонент Spring. Фильтр наследуется от `OncePerRequestFilter` и выполняет проверку в `doFilterInternal(...)`, прежде чем пропустить запрос дальше по цепочке. `RateLimiter` передаётся через конструктор.

### Правила ограничения

Проверяются **POST-запросы** к следующим адресам. Лимит учитывается по сочетанию правила маршрута и IP клиента.

| Маршрут | Максимум попыток | Временное окно |
| --- | --- | --- |
| `/api/auth/login` | 10 | 5 минут |
| `/api/auth/register` и пути с этим префиксом | 10 | 30 минут |
| `/api/surveys/host` | 30 | 10 минут |

Для входа и входа ведущего путь сравнивается через `equals`, для регистрации — через `startsWith`.

### Как работает фильтр

1. Проверяет, что HTTP-метод — `POST`.
2. Находит подходящее правило по URI запроса.
3. Вызывает `limiter.tryAcquire(...)`, передавая ключ из маршрута и IP, максимум попыток и временное окно.
4. Если лимит исчерпан, возвращает `429 Too Many Requests`, задаёт формат `application/json` и кодировку UTF-8, записывает тело ошибки и завершает обработку:

   ```json
   {"message": "Слишком много попыток, попробуйте позже"}
   ```

5. Если запрос разрешён, вызывает `chain.doFilter(request, response)` — передаёт его следующему участнику цепочки.

**Назначение:** ограничить частоту попыток подбора паролей и сканирования кодов опросов. По комментарию в коде, дополнительные ограничения, например по коду опроса при входе ведущего, остаются в контроллерах.

**Связь с архитектурой:** фильтр выполняет общую проверку HTTP-запросов до их обработки контроллером. При превышении лимита он сам формирует ответ в формате `{"message": "..."}`; в этой ветке `ApiErrorHandler` не вызывается. Детали алгоритма подсчёта попыток скрыты в `RateLimiter` и на скриншоте не показаны.

## 7. Контроллер опросов — `SurveyController`

В `SurveyController` из пакета `com.cloudask.web` собраны HTTP-операции с опросами. На скриншотах показаны зависимости, константы, DTO запроса и методы управления опросами.

### Зависимости контроллера

Через конструктор передаются восемь объектов:

| Зависимость | Назначение |
| --- | --- |
| `SurveyRepository` | Доступ к опросам. |
| `ResponseRepository` | Доступ к ответам участников. |
| `SurveyOptionRepository` | Доступ к вариантам ответа. |
| `UserRepository` | Доступ к пользователям. |
| `TokenService` | Работа с токенами. |
| `PasswordEncoder` | Кодирование и проверка секретов. |
| `WsPushService` | Отправка обновлений через WebSocket. |
| `RateLimiter` | Ограничение частоты действий. |

Также внутри класса создаётся `SecureRandom` — генератор криптографически стойких случайных значений. Конкретные места его использования здесь не показаны.

### Как репозитории и сервисы связаны с контроллером

**Репозитории и сервисы являются зависимостями контроллера.** Они объявлены в полях `private final`, передаются параметрами конструктора и сохраняются присваиваниями вида `this.surveys = surveys`.

Spring создаёт контроллер и передаёт ему подходящие объекты из своего контейнера — это **внедрение зависимостей через конструктор (Dependency Injection, DI)**. Если конструктор единственный, отдельная аннотация `@Autowired` для него не требуется.

Контроллер затем вызывает методы этих объектов: например, `surveys.save(...)` для сохранения опроса или `tokens.random(...)` для генерации токена. Репозитории обеспечивают доступ к данным, сервисы выполняют выделенные операции приложения. Направление зависимости здесь — от `SurveyController` к используемым компонентам; обратная ссылка на контроллер им не нужна.

`final` означает, что после инициализации поле нельзя переназначить на другой объект; сам переданный объект при этом не обязательно неизменяемый. В отличие от внедрённых зависимостей, `SecureRandom` в показанном коде создаётся самим контроллером через `new`.

### Ограничения, заданные константами

- Общее окно ограничения: **10 секунд**, максимум — **5**. К каким действиям оно применяется, нужно смотреть в методах контроллера.
- Количество вариантов ответа: от **2 до 10**.
- Ограничение входа ведущего: **5 попыток за 10 минут**. Комментарий связывает его с защитой четырёхзначного PIN: при публичном коде опроса короткий секрет можно быстро перебрать без ограничения попыток.

### DTO создания опроса

```java
public record CreateSurveyRequest(
    @NotBlank @Size(max = 300) String question,
    @NotBlank @Size(min = 4, max = 4) String pin,
    Survey.SurveyType type,
    List<@Size(max = 200) String> options
) {}
```

- `question`: непустой вопрос длиной до 300 символов.
- `pin`: непустая строка ровно из четырёх символов. Хотя комментарий говорит о четырёх цифрах, показанные аннотации проверяют только непустоту и длину; проверка состава символов здесь не видна.
- `type`: тип опроса, заданный `Survey.SurveyType`.
- `options`: список вариантов; у каждого строкового элемента ограничена длина — до 200 символов. Диапазон количества вариантов 2–10 объявлен отдельно константами.

Аннотации описывают ограничения данных. В показанном далее методе `create` аргумент помечен `@Valid @RequestBody`: тело запроса преобразуется в `CreateSurveyRequest` и проходит валидацию.

**Наблюдение об архитектуре:** контроллер связан сразу с четырьмя репозиториями и несколькими вспомогательными компонентами. Это повод проверить распределение обязанностей: операции с опросами и их бизнес-правила можно объединить в сервисе, сократив число прямых зависимостей веб-слоя.

### Методы обработки HTTP-запросов

Один контроллер содержит несколько методов, каждый из которых связан со своим сочетанием HTTP-метода и пути:

| Аннотация и путь | Java-метод | Действие |
| --- | --- | --- |
| `@PostMapping("/api/surveys")` | `create(...)` | Создать опрос. |
| `@GetMapping("/api/surveys")` | `mySurveys()` | Получить опросы текущего пользователя. |
| `@DeleteMapping("/api/surveys/{code}")` | `delete(...)` | Удалить опрос по коду. |
| `@PostMapping("/api/surveys/{code}/close")` | `close(...)` | Закрыть опрос: статус `CLOSED`. |
| `@PostMapping("/api/surveys/{code}/reopen")` | `reopen(...)` | Снова открыть опрос: статус `ACTIVE`. |

`@RequestBody` получает данные из тела запроса, а `@PathVariable` — из участка пути, например `{code}`. Один путь `/api/surveys` обслуживает разные операции благодаря разным HTTP-методам: `GET` и `POST`.

### Создание опроса — `create`

1. Получает текущего пользователя через `currentUser()` и назначает его владельцем.
2. Создаёт `Survey`, записывает вопрос и хеш PIN через `encoder.encode(req.pin())`.
3. Генерирует код длиной 6 символов; повторяет генерацию, пока `existsByCode(...)` обнаруживает совпадение с существующим кодом.
4. Генерирует отдельный `hostToken` длиной 32 символа.
5. Устанавливает тип опроса. Если `type` не передан, используется `FREE_TEXT`.
6. Для типа `CHOICE` нормализует варианты и добавляет объекты `SurveyOption` с их порядковыми индексами.
7. Сохраняет опрос через `surveys.save(s)` и возвращает `ResponseEntity.ok(hostView(s))`.

Метод помечен `@Transactional`: операции с БД внутри него объединяются в транзакцию. Это позволяет сохранить изменения как единое целое; при исключениях, вызывающих откат, изменения отменяются.

### Вспомогательный метод — `normalizeOptions`

`private static List<String> normalizeOptions(List<String> raw)` не является HTTP-обработчиком: это внутренний метод подготовки вариантов ответа.

- Пропускает `null`, обрезает пробелы по краям через `trim()` и удаляет пустые строки.
- Проверяет, что длина каждого оставшегося варианта не превышает 200 символов; иначе возвращается ошибка `400` через исключение.
- Удаляет повторы без учёта регистра. `LinkedHashMap` сохраняет порядок, а `putIfAbsent` — первое написание варианта.
- Проверяет, что после очистки осталось от 2 до 10 уникальных вариантов; иначе выбрасывает исключение со статусом `400`.
- Возвращает неизменяемый список через `List.copyOf(...)`.

Например, `[" Да ", "да", "", "Нет"]` превращается в `["Да", "Нет"]`.

### Список своих опросов — `mySurveys`

Получает текущего пользователя и вызывает `findByOwnerIdOrderByCreatedAtDesc(owner.getId())`. Для каждого опроса формируется `Map` с полями `code`, `question`, `status`, `type`, `createdAt`, `hostToken` и `responses` — количеством ответов из `responses.countBySurveyId(...)`. Возвращается список от новых опросов к старым.

### Удаление и смена статуса

`delete` ищет опрос по коду: если его нет — выбрасывает исключение `404 Not Found`. Если текущий пользователь не владелец — `403 Forbidden`. Затем вызывает `wsPush.evict(s)`, массово удаляет ответы через `responses.deleteAllBySurveyId(...)`, удаляет сам опрос и возвращает `200 OK` без тела. Метод также помечен `@Transactional`.

Методы `close` и `reopen` делегируют работу общему приватному методу `changeStatus(code, status)`. В видимой части он находит опрос, проверяет владельца, устанавливает статус и сохраняет опрос. Это пример устранения дублирования: два HTTP-обработчика используют одну внутреннюю реализацию.

**Главная мысль:** в контроллере есть публичные методы входа для HTTP-запросов и приватные вспомогательные методы. Аннотации маршрутизации определяют, какие методы доступны через API. На этом примере также видно, что значительная часть бизнес-логики пока реализована непосредственно в контроллере.

## 8. Антипаттерн: бизнес-логика внутри контроллера

**«Толстый контроллер»** — контроллер, который помимо обработки HTTP реализует бизнес-правила и управляет целым сценарием работы с данными. Такую логику можно вынести в сервис.

**Правило преподавателя: контроллеры должны быть простыми.** Их основная задача — принять запрос, передать выполнение нужному компоненту и сформировать ответ. Большое количество бизнес-проверок, вычислений и связанных действий внутри контроллера — признак того, что стоит выделить сервис. При этом простой вызов репозитория без самостоятельной бизнес-логики допустим: важна ответственность контроллера, а не обязательное наличие промежуточного класса.

По формулировке преподавателя, **контроллеры должны быть «глупенькими»**:

- **Валидация:** принять запрос и проверить входные данные.
- **Контроль ошибок:** обеспечить корректный HTTP-ответ при ошибке; общую обработку можно делегировать `@RestControllerAdvice`.
- **Передача в сервис:** делегировать бизнес-сценарий сервису, затем сформировать ответ клиенту.

Контроллер координирует обработку HTTP, а основные бизнес-правила и вычисления находятся в сервисе.

### Пример: регистрация в `AuthController`

На скриншоте метод `register(...)` с `@PostMapping("/register/{inviteToken}")` выполняет сразу несколько действий:

1. Нормализует email: удаляет пробелы по краям и переводит в нижний регистр с `Locale.ROOT`.
2. Ищет приглашение по токену. Если его нет — выбрасывает ошибку `404 Not Found`.
3. Проверяет, что приглашение не использовано и не просрочено; иначе — `410 Gone`.
4. Проверяет уникальность email; если он уже зарегистрирован — `409 Conflict`.
5. Создаёт пользователя и хеширует пароль через `PasswordEncoder`.
6. Назначает роль: первый зарегистрированный пользователь получает `ADMIN`, остальные — `MODERATOR`.
7. Сохраняет пользователя, затем отмечает приглашение использованным: записывает ID пользователя и время использования, сохраняет приглашение.
8. Вызывает `authenticate(...)` и возвращает сведения о текущем пользователе через `ResponseEntity.ok(currentUserInfo())`.

Это уже бизнес-сценарий регистрации: проверка права на регистрацию, уникальности пользователя, назначение роли и изменение нескольких сущностей.

### Как разделить обязанности

| Controller | Service, например `RegistrationService` |
| --- | --- |
| Получить токен из пути и DTO из тела запроса. | Нормализовать email и проверить приглашение. |
| Запустить валидацию DTO через `@Valid`. | Проверить уникальность email, создать пользователя и назначить роль. |
| Вызвать сервис регистрации. | Хешировать пароль, сохранить пользователя и отметить приглашение использованным. |
| Выполнить необходимую работу с HTTP-сессией и сформировать ответ. | Объединить связанные изменения БД в транзакцию. |

В результате бизнес-правила проще проверять отдельно от HTTP и повторно использовать. Контроллер остаётся точкой входа и делегирует выполнение сценария сервису.

Показанный рядом `login(...)` короче: вызывает `authenticate(...)` и возвращает информацию о пользователе. Реализация `authenticate(...)` на этом скриншоте не видна.

**Отличие от допустимого прямого обращения к Repository:** простой запрос данных может не требовать сервиса. Несколько бизнес-проверок и согласованных изменений, как при регистрации, — основание выделить сервисный метод.

## 9. Пример сервиса — `WsPushServiceImpl`

```java
public class WsPushServiceImpl implements WsPushService {
    // ...
}
```

`WsPushService` — интерфейс, задающий контракт, а `WsPushServiceImpl` — его реализация. В контроллере зависимость объявлена через интерфейс `WsPushService`: конкретные детали подготовки и отправки обновлений скрыты в реализации.

### Методы сервиса

| Метод | Назначение |
| --- | --- |
| `wordsFor(survey)` | Возвращает список слов с их частотами — `List<WordAggregationService.WordCount>`. |
| `resultsFor(survey)` | Возвращает результаты вариантов ответа — `List<ResultService.OptionResult>`. |
| `aggregateFor(survey)` | Внутренний метод получения или вычисления агрегированных результатов с кешированием. |
| `publishState(survey)` | Отправляет статус опроса и количество ответов в `/topic/surveys/{code}/state`. |
| `evict(survey)` | Удаляет кеш агрегата для указанного опроса. |
| `pushAggregate(surveyId)` | Находит опрос и отправляет его агрегированные результаты подписчикам. |

### Подготовка и кеширование результатов

Внутренний метод `aggregateFor(...)`:

1. Получает ID опроса и текущее количество ответов через `responses.countBySurveyId(id)`.
2. Ищет сохранённый агрегат в `cache` по ID.
3. Если кеш есть и число ответов совпадает с сохранённым, возвращает готовый агрегат.
4. Иначе вычисляет результат в зависимости от типа опроса:
   - `CHOICE` — вызывает `resultService.resultsFor(id)`;
   - свободный текст — получает тексты через `responses.findTextsBySurveyId(id)` и передаёт их в `aggregator.aggregate(...)`.
5. Сохраняет в кеше количество ответов вместе с агрегатом и возвращает результат.

Кеш позволяет повторно использовать вычисленный результат. В показанном коде критерием его актуальности служит **совпадение количества ответов**.

### Отправка обновлений

`publishState(...)` использует `messaging.convertAndSend(...)` для отправки объекта с полями `status` и `responses`.

`pushAggregate(...)` записывает время отправки в `lastWordsPush`, затем ищет опрос через `surveys.findById(...)`. Для `CHOICE` отправляет результаты в `/topic/surveys/{code}/results`, для свободного текста — частоты слов в `/topic/surveys/{code}/words`. Если опрос уже удалён, пропускает отправку и пишет отладочное сообщение в лог.

**Архитектурная роль:** сервис координирует репозитории, вычисление результатов, кеш и отправку сообщений. Контроллеру достаточно вызвать операцию через интерфейс; реализовывать эту последовательность внутри HTTP-обработчика не требуется.

## 10. Цепочка Controller → Service → Repository

Пример GET-обработчика в `SurveyController`:

```java
@GetMapping("/api/surveys/public/{code}/words")
public List<WordAggregationService.WordCount> words(@PathVariable String code) {
    Survey s = surveys.findByCode(code)
        .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND));
    return wsPush.wordsFor(s);
}
```

Контроллер находит опрос через `SurveyRepository`, затем вызывает `wordsFor(...)` у зависимости типа `WsPushService`. Выполнение передаётся реализации `WsPushServiceImpl`, которая использует репозиторий ответов `responses` и сервис агрегации.

```text
GET-запрос → SurveyController
                 ├── SurveyRepository: найти опрос
                 └── WsPushService (интерфейс)
                          ↓ реализация
                     WsPushServiceImpl
                          ├── ResponseRepository: получить данные ответов
                          └── WordAggregationService: подсчитать слова
```

Аналогичный GET-обработчик `/api/surveys/public/{code}/results` вызывает `wsPush.resultsFor(s)` для получения результатов по вариантам ответа. Интерфейс задаёт доступные операции сервиса, реализация определяет, как их выполнить, а репозиторий отвечает за доступ к данным.

## 11. Репозиторий: готовые методы и собственные запросы

```java
public interface ResponseRepository extends JpaRepository<Response, Long> {
    // Дополнительные методы работы с ответами
}
```

`Response` — тип сущности, `Long` — тип её идентификатора. Репозиторий объявлен интерфейсом; реализацию доступа к данным предоставляет Spring Data JPA.

### 1. Базовые методы `JpaRepository`

Доступны благодаря наследованию: например, `save(...)`, `findById(...)`, `findAll()`, `count()` и `delete(...)`. Для них не требуется писать собственный запрос.

### 2. Запросы, построенные по имени метода

Spring Data формирует запрос по названию объявленного метода:

| Метод из примера | Назначение |
| --- | --- |
| `countBySurveyId(surveyId)` | Посчитать ответы опроса. |
| `countBySurveyIdAndParticipantIdAndCreatedAtAfter(surveyId, participantId, after)` | Посчитать ответы участника в опросе после указанного времени. |
| `findFirstBySurveyIdAndParticipantIdOrderByIdAsc(surveyId, participantId)` | Найти первый ответ участника в опросе по возрастанию ID; результат — `Optional<Response>`. |

Эти методы добавлены в `ResponseRepository`: они не являются готовыми базовыми методами `JpaRepository`, хотя текст запроса для них тоже не пишется вручную.

### 3. Явные запросы через `@Query`

```java
@Query("select r.text from Response r where r.survey.id = :surveyId")
List<String> findTextsBySurveyId(@Param("surveyId") UUID surveyId);
```

Запрос выбирает только тексты ответов указанного опроса. `@Param` связывает аргумент Java-метода с именованным параметром `:surveyId`.

**Уточнение:** на скриншоте показан JPQL — запрос к сущности `Response` и её Java-полям. Он похож на SQL, но это не прямой SQL-запрос к таблице. Native SQL можно задать отдельно через `@Query(..., nativeQuery = true)`.

Для подсчёта голосов по вариантам используется группировка:

```java
@Query("select r.option.id as optionId, count(r) as cnt "
     + "from Response r where r.survey.id = :surveyId group by r.option.id")
List<OptionCount> countVotesBySurveyId(@Param("surveyId") UUID surveyId);
```

Результат представлен интерфейсной проекцией — только нужными полями вместо целой сущности:

```java
interface OptionCount {
    Long getOptionId();
    long getCnt();
}
```

### Массовое удаление

```java
@Modifying
@Query("delete from Response r where r.survey.id = :surveyId")
int deleteAllBySurveyId(@Param("surveyId") UUID surveyId);
```

`@Modifying` указывает, что запрос изменяет данные. Метод удаляет ответы опроса одной массовой операцией и возвращает количество удалённых строк. В показанном ранее `delete(...)` контроллера этот вызов выполняется внутри транзакции.

**Главная мысль:** слой Repository скрывает детали получения и изменения данных. В нём можно сочетать базовые операции, запросы по имени метода и явно написанные запросы; сервис использует их для выполнения своего сценария.

## 12. Зачем разделять приложение на слои

### 1. Менять пользовательский интерфейс, не переписывая логику

Новый дизайн, мобильное приложение и Telegram-бот могут использовать одну бизнес-логику. Меняется способ взаимодействия с пользователем, а правила приложения остаются общими. Например, веб-интерфейс и бот платформы курса могут иметь разные контроллеры, обращающиеся к одним сервисам.

Здесь под интерфейсом понимается способ взаимодействия с пользователем, а не Java-интерфейс сервиса.

### 2. Тестировать логику без базы данных

При проверке сервиса нижний слой можно заменить заглушкой: вместо реального репозитория передать объект с заранее заданным поведением. Это позволяет проверить бизнес-правила без запуска БД. Контракт зависимости определяет, какие операции должна поддерживать такая замена.

### 3. Читать чужой код по ролям

Разделение обязанностей помогает ориентироваться в проекте: найти контроллер нужного запроса, посмотреть, кому он делегирует работу, затем перейти к сервису и репозиторию. Вместо последовательного чтения всех файлов — движение по цепочке вызовов и зависимостей.

### Цена разделения

**Слои добавляют файлы, интерфейсы и переходы между классами.** Их стоит вводить там, где они помогают менять, тестировать и понимать код. Не каждому приложению и не каждой операции нужны все четыре слоя: простой доступ к данным может обходиться без отдельного сервиса.

На слайде преподаватель анонсирует пример Spring PetClinic, в котором отсутствует один из четырёх слоёв; какой именно и почему — будет разобрано далее.

## 13. SOLID: пять принципов проектирования

SOLID — словарь для обсуждения обязанностей классов, контрактов и зависимостей. На этой лекции основной акцент на **S, I и D**.

| Принцип | Смысл | Связь с примерами лекции |
| --- | --- | --- |
| **S — Single Responsibility** (единственная ответственность) | У класса одна причина меняться. Это не требование иметь только один метод. | Контроллер меняется при изменении взаимодействия с клиентом, репозиторий — при изменении хранения данных. |
| **O — Open/Closed** (открытость/закрытость) | Расширять поведение, по возможности не изменяя существующий код. | Подробный разбор преподаватель относит к паре 11. |
| **L — Liskov Substitution** (подстановка Лисков) | Подтип должен заменять базовый тип без нарушения его контракта. | Пример со слайда: `LinkedHashMap` вместо `HashMap` сохраняет контракт операций, добавляя определённый порядок обхода. |
| **I — Interface Segregation** (разделение интерфейсов) | Узкие интерфейсы предпочтительнее перегруженных: клиенту не нужны зависимости от неиспользуемых операций. | Контракт сервиса предоставляет нужный набор методов. |
| **D — Dependency Inversion** (инверсия зависимостей) | Зависеть от абстракций; детали реализации должны соответствовать этим абстракциям. | Контроллер получает интерфейс сервиса, а не привязывается к конкретному классу реализации. |

**Важно различать:** Dependency Injection (DI) — способ передать зависимости объекту; Dependency Inversion (D в SOLID) — принцип организации зависимостей. Передача конкретного класса через конструктор сама по себе ещё не означает соблюдения D.

**Позиция преподавателя:** SOLID — не пять безусловных запретов. От принципов можно осознанно отступать, но их нужно понимать, чтобы обсуждать архитектурные решения и проводить ревью кода.

Поддерживаются два альтернативных способа сборки: **Maven** (`pom.xml`) и **Gradle** (`build.gradle`, `settings.gradle`). Скрипты `mvnw` и `gradlew` — обёртки для запуска соответствующего инструмента сборки.

- **Checkstyle** проверяет исходники по заданным правилам. На экране открыт `nohttp-checkstyle.xml`: в нём подключена проверка `NoHttpCheck` и файл исключений `nohttp-checkstyle-suppressions.xml`.

- `application.properties` содержит общие настройки; файлы с суффиксами `mysql` и `postgres` — настройки соответствующих профилей БД.

- `messages` хранит текстовые сообщения, в том числе варианты для разных языков. **Локализация** позволяет менять язык интерфейса без переписывания Java-кода и шаблонов для каждого перевода.

**Наблюдение о структуре:** в отличие от CloudAsk с общими пакетами `web`, `service`, `repo`, здесь видны пакеты по предметным областям — `owner` и `vet`, а также общие `model` и `system`. Роли классов и зависимости нужно изучать внутри этих пакетов: названия папок сами по себе не определяют число архитектурных слоёв.

## 15. Организация по фичам — package by feature

В PetClinic верхний уровень пакетов организован по функциональным областям, а не по техническим слоям:

- `model` — общие базовые классы модели: `BaseEntity`, `NamedEntity`, `Person`.
- `owner` — функциональность владельцев, их животных и посещений.
- `vet` — функциональность ветеринаров.
- `system` — общая системная часть приложения.

**Основная идея:** классы, относящиеся к одной фиче, собираются в одном пакете. Например, внутри `owner` находятся:

```text
owner/
├── Owner                 — сущность владельца
├── OwnerController       — обработка запросов о владельцах
├── OwnerRepository       — доступ к данным владельцев
├── Pet                   — сущность животного
├── PetController
├── PetType
├── PetTypeFormatter
├── PetTypeRepository
├── PetValidator
├── Visit                 — сущность посещения
└── VisitController
```

Таким образом, сущности находятся не только в `model`: общие базовые классы вынесены туда, а конкретные сущности расположены рядом с остальным кодом своей функциональной области.

### По слоям и по фичам: два способа группировки

| По слоям — package by layer | По фичам — package by feature |
| --- | --- |
| Общие пакеты `web`, `service`, `repo`, `entity`. | Пакеты `owner`, `vet` и другие функциональные области. |
| Контроллеры разных фич лежат вместе, как и репозитории. | Контроллер, репозиторий и сущности одной фичи лежат рядом. |
| Для изучения фичи нужно переходить между пакетами слоёв. | Основной код фичи можно изучать внутри её пакета. |

При росте фичи её пакет можно дополнительно разделить, например на `owner.web`, `owner.service`, `owner.repo`. Получится сочетание: сначала группировка по функциональности, затем по техническим ролям внутри неё.

**Уточнение формулировки «нет слоистой архитектуры»:** здесь нет общего разбиения пакетов по слоям. Это не отменяет ролей Controller и Repository или правил направления зависимостей. Организация файлов по фичам и разделение ответственности по слоям могут сочетаться.

### Где находятся слои при разбиении по фичам

Слои определяются назначением классов и их аннотациями, а не наличием папки `controllers`: `@Controller` обозначает веб-компонент, `@Repository` — компонент доступа к данным, `@Entity` — сущность модели хранения. При использовании Spring Data интерфейс репозитория также определяется наследованием от соответствующего интерфейса, например `JpaRepository`; отдельная аннотация `@Repository` на нём не обязательна.

Слайд дополняет состав пакетов: в `vet` находятся `Vet`, `VetController`, `VetRepository`, а в `system` — `CrashController` и `WelcomeController`.

**Способ разбиения проекта — архитектурное решение:**

- **По фичам:** вся функциональная область рядом; в небольшом проекте её быстрее понять. Границы фич в дальнейшем могут стать основой границ модулей или отдельных сервисов.
- **По слоям:** компоненты одной технической роли собраны вместе; это удобно при работе сразу над целым слоем, например при замене механизма хранения данных.

Выбор зависит от того, какие части проекта нужно понимать и менять совместно. Оба способа сохраняют необходимость разделять ответственность компонентов.

### Пример `OwnerController`

В показанном коде `OwnerController` получает `OwnerRepository` через конструктор. Метод обработки формы создания проверяет `BindingResult`, при ошибках возвращает форму, а при успехе вызывает `owners.save(owner)` и перенаправляет пользователя на страницу владельца.

Здесь используется `@Controller`: возвращаемые строки обозначают имена шаблонов или перенаправления, например `owners/createOrUpdateOwnerForm` и `redirect:/owners/{id}`. Это отличается от показанных ранее REST-контроллеров CloudAsk, возвращающих данные в теле ответа.

**Отдельного сервисного слоя в рассматриваемом варианте PetClinic нет:** контроллер обращается к репозиторию напрямую для простых операций. Это иллюстрирует уточнение преподавателя: сервис не требуется только ради передачи вызова репозиторию.

### Прямые обращения к репозиторию в `OwnerController`

На следующем фрагменте видны ещё два примера цепочки `Controller → Repository → БД`.

**Поиск владельцев с пагинацией:** внутренний метод `findPaginatedForOwnersLastName(...)` задаёт размер страницы 5 записей, ограничивает номер страницы снизу единицей и создаёт `PageRequest`. Затем напрямую вызывает:

```java
return owners.findByLastNameStartingWith(lastname, pageable);
```

Пользовательская нумерация страниц начинается с 1, а в `PageRequest` — с 0, поэтому передаётся `validatedPage - 1`. Метод `addPaginationModel(...)` добавляет в модель `currentPage`, `totalPages`, `totalItems` и `listOwners`, после чего возвращает имя шаблона `owners/ownersList`.

**Обновление владельца:** обработчик `POST /owners/{ownerId}/edit` проверяет ошибки формы через `BindingResult` и соответствие ID владельца в модели идентификатору из URL. При успешной проверке устанавливает ID, вызывает `owners.save(owner)`, добавляет сообщение об успехе и возвращает перенаправление на страницу владельца.

**Вывод преподавателя:** наличие контроллеров, работающих непосредственно с репозиториями, допустимо. Обработка формы, подготовка данных для шаблона и простой вызов репозитория сами по себе не требуют промежуточного сервиса. Сервис выделяют при появлении самостоятельной бизнес-логики.

## 16. Как перейти от интерфейса в браузере к коду

Практический способ изучения проекта — начать с действия пользователя в UI и найти его реализацию:

1. Посмотреть в браузере нужную страницу или действие: какой URL используется, что делает форма или кнопка.
2. Найти в проекте соответствующий маршрут или ключевое слово. В устном примере преподавателя — поиск по `vote`.
3. Найти метод контроллера и его аннотацию маршрутизации.
4. Проследить вызовы сервиса и репозитория, затем посмотреть, какой ответ или шаблон возвращается пользователю.

Так связываются видимое поведение и реализация: `UI → HTTP-запрос → Controller → дальнейшие вызовы → ответ`. На приложенных скриншотах показан поиск владельцев в `OwnerController`, а не метод `vote`.

### Пример: поиск владельцев в PetClinic

- `GET /owners/find` возвращает шаблон формы `owners/findOwners`.
- `GET /owners` обрабатывается методом `processFindForm(...)`: он получает номер страницы (по умолчанию 1) и фамилию из объекта `Owner`.
- Если фамилия отсутствует, используется пустая строка — поиск без ограничения по префиксу фамилии. Иначе пробелы по краям удаляются через `strip()`.
- Контроллер вызывает `findPaginatedForOwnersLastName(...)`, который обращается к репозиторию.
- Если номер страницы выходит за допустимые границы, выполняется перенаправление на первую страницу с сохранением непустого условия поиска.
- Если владельцы не найдены, в `BindingResult` добавляется ошибка поля `lastName` и снова возвращается форма поиска.
- Если найден ровно один владелец, выполняется перенаправление на его страницу.
- Если результатов несколько, они передаются в модель вместе с параметрами пагинации и показываются списком.

Это пример логики представления в контроллере: выбрать форму, список или перенаправление в зависимости от результата поиска.

## 17. Базовый путь контроллера

У контроллера можно задать общий префикс маршрутов через **`@RequestMapping` над классом**. Путь конкретного метода дополняет этот префикс.

Условный пример организации маршрута голосования:

```java
@RestController
@RequestMapping("/api/surveys")
public class SurveyController {
    @PostMapping("/public/{code}/vote")
    public ResponseEntity<?> vote(@PathVariable String code) {
        // Обработка голоса
        return ResponseEntity.ok().build();
    }
}
```

Итоговый маршрут: **`POST /api/surveys/public/{code}/vote`**. Значение `{code}` берётся из URL через `@PathVariable`.

Можно также не задавать префикс класса и указывать весь путь в каждой аннотации метода — как в показанных ранее методах `SurveyController`.

**Для поиска по коду:** полный URL не всегда встречается одной строкой. Нужно учитывать базовый путь класса и путь метода, а конкретное значение в URL заменять параметром маршрута: например, искать `vote` или `/public/{code}/vote`, а не весь адрес с кодом определённого опроса.

## 18. Проверки данных в контроллере

**Проверять входные данные в контроллере — нормальная практика.** Требование простоты контроллера не означает, что в нём не должно быть проверок вообще.

На примере `vote(...)`, обрабатывающего `POST /api/surveys/public/{code}/vote`, показаны следующие проверки:

- DTO `VoteRequest` содержит `@NotNull Long optionId`, а аргумент метода — `@Valid @RequestBody`: идентификатор варианта обязателен.
- Контроллер получает активный опрос через `findActive(code)` и проверяет его тип. Если это не `CHOICE`, выбрасывает ошибку `400 Bad Request` с сообщением, что в этом опросе ответ даётся свободным текстом.
- Вызов `surveyOptions.findByIdAndSurveyId(req.optionId(), s.getId())` проверяет одновременно существование варианта и его принадлежность текущему опросу. Если такого сочетания нет — ошибка `400` «Такого варианта нет в этом опросе».
- После получения ID участника проверяется ограничение частоты. При превышении возвращается `429 Too Many Requests` с сообщением «Слишком часто, подождите немного».

**Почему проверяется принадлежность:** корректного числового `optionId` недостаточно — клиент может передать ID варианта из другого опроса. Сервер должен проверять данные в контексте конкретной операции.

Далее виден поиск существующего ответа участника через `responses.findFirstBySurveyIdAndParticipantIdOrderByIdAsc(...)`. По комментарию в коде, повторное голосование за другой вариант обновляет существующий ответ: один голос на участника.

**Граница ответственности:** простые проверки запроса могут оставаться в контроллере. Правила предметной области — например, принадлежность варианта опросу и порядок повторного голосования — при выделении полноценного сервиса голосования следует выполнять в нём, чтобы они действовали для всех вызывающих компонентов. Повод для переноса — усложнение и повторное использование сценария, а не сам факт наличия `if`.

### Слишком частое голосование

Если отправлять голоса много и быстро, проверка `overRateLimit(s.getId(), pid)` срабатывает для сочетания **опрос + участник**. Контроллер сразу возвращает **`429 Too Many Requests`** с текстом «Слишком часто, подождите немного»; до сохранения голоса выполнение не доходит. После этого нужно подождать, прежде чем повторять попытку. Реализация `overRateLimit(...)` на данном скриншоте не показана.

В этой ветке ответ формируется напрямую через `.body("Слишком часто, подождите немного")`: тело содержит строку, а не объект `ErrorBody` с полем `message`.

Если ограничение не превышено, обработка продолжается:

1. Репозиторий ищет существующий ответ участника в текущем опросе.
2. Если ответа нет, создаётся `Response`; если есть — обновляется текст выбранного варианта.
3. Через `setOption(option)` записывается выбранный вариант, затем `responses.save(r)` сохраняет ответ.
4. Вызываются `wsPush.onResponsesChanged(s)` и `wsPush.publishState(s)` для обновления результатов и состояния у подписчиков.
5. Клиент получает `200 OK` без тела.

Повторный голос меняет выбор участника, а ограничение частоты защищает обработчик от слишком частых запросов. Это два отдельных правила.

## 19. Один запрос от URL до базы: `GET /owners`

**Рецепт чтения чужого кода:** выбрать один запрос и пройти по цепочке его обработки вместо чтения всех файлов подряд.

```text
Браузер: GET /owners
    → OwnerController: принять запрос, подготовить поиск
    → OwnerRepository: запросить владельцев
    → БД: получить данные
    → контроллер: подготовить модель и выбрать шаблон
    → HTML-страница в браузере
```

На слайде в качестве БД указаны H2, MySQL и PostgreSQL. Конкретная БД выбирается конфигурацией приложения.

| Аннотация | Роль компонента |
| --- | --- |
| `@Controller` | Принимает HTTP-запросы. Маршрут связан с методом класса; в рассматриваемом MVC-примере возвращаемая строка задаёт имя шаблона страницы или перенаправление. |
| `@Repository` | Обозначает компонент доступа к данным. Вызывающий код работает с операциями сохранения и поиска, не управляя SQL напрямую. В Spring Data роль репозитория может задаваться наследованием интерфейса, без явной `@Repository`. |
| `@Entity` | Обозначает сущность JPA: её состояние отображается на данные в таблицах. Например, объекты `Owner` загружаются и сохраняются через репозиторий. |

### Точка запуска PetClinic

```java
@SpringBootApplication
public class PetClinicApplication {
    public static void main(String[] args) {
        SpringApplication.run(PetClinicApplication.class, args);
    }
}
```

Точка входа запускает Spring Boot. Затем фреймворк на основе конфигурации, аннотаций и интерфейсов репозиториев создаёт компоненты, связывает зависимости и регистрирует обработчики запросов.

**Связь с предыдущими примерами:** приём запроса, обращение к данным и возврат результата прослеживаются так же, как при голосовании в CloudAsk. В PetClinic показанная цепочка короче: между контроллером и репозиторием нет отдельного сервиса, а результат отображается как HTML-страница.

### Читать контроллер целиком: методы и их роли

В `OwnerController` собраны методы обработки запросов о владельцах и вспомогательные методы этого контроллера. При разборе нужно смотреть не только на один маршрут, но и на подготовку данных, используемую его обработчиком.

На скриншоте видны:

- **Конструктор** — получает `OwnerRepository` и сохраняет его в поле `owners`.
- **`setAllowedFields(...)` с `@InitBinder`** — настраивает привязку данных запроса к объектам: запрещает заполнять поля `id` и `*.id` через механизм привязки формы.
- **`findOwner(...)` с `@ModelAttribute("owner")`** — подготавливает атрибут модели `owner` перед обработкой запроса. Если `ownerId` отсутствует, создаёт новый `Owner`; иначе загружает его через `owners.findById(...)`. Если владелец не найден, выбрасывает `IllegalArgumentException`.
- **`initCreationForm()` с `@GetMapping("/owners/new")`** — возвращает имя шаблона формы создания владельца.
- **`processCreationForm(...)` с `@PostMapping("/owners/new")`** — принимает и проверяет заполненную форму, затем сохраняет владельца либо снова показывает форму с ошибками.

**Важно:** не каждый метод внутри контроллера является отдельным HTTP-маршрутом. Аннотации определяют его роль: обработка запроса, подготовка модели или настройка привязки данных. Реализация хранения при этом остаётся в репозитории.

## 20. Spring: управление объектами, DI и Spring Data JPA

**Одна из основных идей Spring — контейнер управляет компонентами и их зависимостями.** Разработчик описывает классы и связи, а фреймворк создаёт необходимые экземпляры, связывает их и вызывает обработчики при поступлении запросов. Это инверсия управления (IoC); внедрение зависимостей (DI) — часть этого механизма.

На примере `OwnerController`:

1. Spring обнаруживает контроллер благодаря `@Controller` и сканированию компонентов.
2. Spring Data создаёт объект, реализующий интерфейс `OwnerRepository`.
3. Контейнер передаёт этот объект в конструктор `OwnerController`.
4. При HTTP-запросе Spring MVC находит подходящий метод по аннотации маршрута и вызывает его, подготавливая аргументы.
5. Код контроллера вызывает `owners.findById(...)` или `owners.save(...)`; инфраструктура репозитория выполняет операцию с данными.

**Уточнение:** Spring создаёт экземпляры управляемых компонентов, а не «вызывает класс». Обращение к репозиторию происходит там, где оно явно предусмотрено кодом контроллера, сервиса или другого компонента.

### Что даёт Spring Data JPA

Можно использовать готовые операции репозитория, объявлять собственные методы поиска по правилам именования и писать явные запросы через `@Query`.

```text
Готовые методы:       findById(...), save(...), findAll(...)
Запрос по имени:      findByLastNameStartingWith(...)
Явный запрос:         @Query("select ...")
```

**Разделение механизмов:** JPA задаёт правила работы с сущностями и их отображения на БД; провайдер JPA, например Hibernate, реализует эту работу. Spring Data JPA добавляет удобную абстракцию репозиториев. Поэтому разработчик может пользоваться готовыми конструкциями и дополнять их собственными запросами, не реализуя весь доступ к данным вручную.

### Сервис — такой же управляемый компонент

**Сервис, как и контроллер, — обычный Java-класс.** Аннотация `@Service` обозначает его роль и позволяет Spring обнаружить его при сканировании компонентов. В показанном примере:

```java
@Service
public class WsPushServiceImpl implements WsPushService {
    // Зависимости передаются через конструктор
}
```

Spring создаёт экземпляр `WsPushServiceImpl` и передаёт в его конструктор необходимые компоненты:

- `SimpMessagingTemplate` — отправка сообщений;
- `ResponseRepository` и `SurveyRepository` — доступ к данным;
- `WordAggregationService` — агрегация слов;
- `ResultService` — подготовка результатов голосования.

Для зависимостей, объявленных через интерфейсы, контейнер подбирает подходящие зарегистрированные реализации. Затем объект `WsPushServiceImpl` можно внедрить в контроллер как `WsPushService`.

**Уточнение:** Spring передаёт необходимые зависимости, а не все существующие реализации. Если одному типу соответствуют несколько кандидатов, выбор нужно определить, например через `@Qualifier` или `@Primary`.

Объекты, созданные внутри класса явно через `new`, создаёт сам код: на скриншоте это кеши на основе `ConcurrentHashMap` и планировщик. Метод `shutdown()` с `@PreDestroy` останавливает планировщик при уничтожении компонента контейнером.

## 21. Интерфейс репозитория без написанной вручную реализации

**Одна из возможностей Spring Data JPA: разработчик описывает контракт репозитория, а фреймворк предоставляет его реализацию при запуске.** Поэтому отдельного класса `OwnerRepositoryImpl` в проекте может не быть.

Пример со слайда:

```java
public interface OwnerRepository extends JpaRepository<Owner, Integer> {
    Page<Owner> findByLastNameStartingWith(String lastname, Pageable pageable);

    Optional<Owner> findById(Integer id);
}
```

- `JpaRepository<Owner, Integer>` задаёт тип сущности и её ключа, а также предоставляет базовые операции работы с данными.
- `findByLastNameStartingWith(...)` описывает поиск по началу фамилии. Spring Data разбирает имя метода и формирует запрос с условием, соответствующим `LIKE 'префикс%'`.
- `Pageable` передаёт параметры страницы и сортировки, а `Page<Owner>` содержит найденные записи и сведения о пагинации.
- `Optional<Owner>` у `findById(...)` означает, что запись может отсутствовать. Этот метод уже предусмотрен базовым репозиторием; здесь он явно объявлен повторно.

Spring Data создаёт прокси-объект репозитория, связывающий готовые операции и методы запросов с инфраструктурой JPA. Spring Boot помогает автоматически настроить эту инфраструктуру, а контейнер внедряет репозиторий в конструктор контроллера.

**Связь с D из SOLID:** контроллер зависит от контракта `OwnerRepository`, а не от конкретного JDBC-класса. Реализация доступа к данным скрыта за интерфейсом.

**Граница этой возможности:** Spring не реализует произвольные интерфейсы автоматически. Для обычного сервисного интерфейса, например `WsPushService`, по-прежнему нужна зарегистрированная реализация. Репозитории Spring Data поддерживаются специальным механизмом; методы должны соответствовать его правилам либо иметь явно заданную реализацию или запрос.

По исторической справке со слайда, в PetClinic раньше был большой интерфейс `ClinicService`, который затем заменили репозиториями по функциональным областям. Имя сохранилось в `ClinicServiceTests`. Это пример того, что архитектура проекта меняется вместе с распределением обязанностей.

## 22. Тестирование по слоям: контроллер без БД

**Разделение зависимостей позволяет проверить контроллер отдельно от реального хранилища.** Вместо репозитория с подключением к БД в контроллер передаётся тестовая замена того же типа.

**Вывод преподавателя:** контроллер можно протестировать без СУБД, подменив репозиторий мок-объектом. В тесте задают ожидаемые результаты его методов — например, найденного владельца или отсутствие записи — и проверяют реакцию контроллера. Мок имитирует поведение зависимости, а не работу всей базы данных.

Пример со слайда — `src/test/.../owner/OwnerControllerTests.java`:

```java
@WebMvcTest(OwnerController.class)
class OwnerControllerTests {
    @Autowired
    private MockMvc mockMvc;

    @MockitoBean
    private OwnerRepository owners;
}
```

| Инструмент | Роль в тесте |
| --- | --- |
| `@WebMvcTest(OwnerController.class)` | Загружает срез веб-слоя с указанным контроллером и необходимой MVC-инфраструктурой, без запуска всего приложения и реального репозитория. |
| `MockMvc` | Позволяет выполнять тестовые HTTP-запросы через Spring MVC и проверять ответы без запуска настоящего браузера и HTTP-сервера. |
| `@MockitoBean` | Регистрирует мок `OwnerRepository`: его поведение задаётся в тесте, реальная БД не используется. |
| `@Autowired` | Внедряет настроенный `MockMvc` в тестовый класс. |

Контроллер получает зависимость через привычный конструктор и работает с тем же контрактом репозитория. Тест может заранее задать, какие записи вернёт поиск, а затем проверить статус ответа, выбранный шаблон, модель, ошибки формы или перенаправление.

**Что такой тест не проверяет:** корректность SQL, отображение сущностей и фактическое сохранение данных в БД. Для проверки слоя репозиториев используется `@DataJpaTest`: он настраивает JPA-срез и работу с тестовой БД. Конкретная БД зависит от конфигурации теста.

Тесты также организованы по фичам: пакет `src/test/.../owner/` соответствует функциональной области `owner` в `src/main`. По слайду, в проекте есть и `MySqlIntegrationTests`, и `PostgresIntegrationTests` для интеграционных проверок с соответствующими БД.

**Связь с причиной № 2 разделения на слои:** поведение веб-слоя можно проверять без инфраструктуры хранения. Такой тест обычно легче и быстрее полного интеграционного теста; точное время выполнения зависит от окружения.

## 23. Главный вопрос архитектуры: «Почему именно так?»

При изучении проекта нужно не только определить его структуру, но и понять причины решений.

### Почему в PetClinic нет Service-слоя?

В рассматриваемых операциях мало бизнес-логики: сохранить владельца, найти по фамилии. Контроллеры обращаются к репозиториям напрямую; отдельный сервис лишь перенаправлял бы те же вызовы и добавлял файлы без практической пользы. По слайду, исторически `ClinicService` существовал, но его убрали.

**Проверка необходимости сервиса:** если он только перекладывает вызов в репозиторий, для такой операции он может быть лишним. Слой нужен для конкретной ответственности, а не ради полного набора слоёв.

### Почему пакеты организованы по фичам?

Для небольшого проекта удобно читать всю функциональную область в одном месте. При развитии приложения границы фич могут стать границами модулей или отдельных сервисов. Разбиение по слоям полезно для другого характера работы — например, когда нужно изменить весь механизм хранения сразу.

### Сравнение двух примеров лекции

| Проект | Организация | Причина решения |
| --- | --- | --- |
| CloudAsk | Общие пакеты по слоям: `web`, `service`, `repo`, `entity`; в коде есть и прямые обращения контроллеров к репозиториям. | Разделение технических обязанностей, выделение операций в сервисы. |
| PetClinic | Пакеты по фичам; в рассматриваемой версии нет отдельного Service-слоя. | Связанный код расположен рядом, простые операции не требуют промежуточного сервиса. |

**Вывод:** оба подхода могут быть осознанными. Вопрос «Почему именно так?» следует задавать любому проекту, включая свой: какую задачу решает выбранная структура и оправдывает ли она свою сложность?

## 24. Пример для ревью: SQL внутри контроллера

На слайде предложен фрагмент `ReportController.java` (импорты и внедрение зависимости опущены):

```java
@Controller
public class ReportController {
    private final JdbcTemplate jdbc; // SQL прямо здесь

    @GetMapping("/report")
    public String report(Model model) {
        List<Map<String, Object>> rows =
            jdbc.queryForList("SELECT * FROM submissions");
        // ... считаем итоги, строим ответ...
        return "report";
    }
}
```

**Вопрос: что скажет ревьюер?**

1. Всё в порядке — работает же.
2. SQL в контроллере — нарушены границы.
3. Не хватает комментариев.
4. Вынести в утилитный класс — и нормально.

**Правильный ответ: 2 — SQL в контроллере нарушает границы ответственности.** Контроллер одновременно принимает HTTP-запрос, знает детали хранения и рассчитывает итоги. Изменение схемы БД или правил отчёта потребует менять веб-компонент.

### Как разделить обязанности

- **`ReportRepository`** выполняет SQL и возвращает данные для отчёта. Использовать внутри него `JdbcTemplate` допустимо: проблема в расположении SQL, а не в самом инструменте.
- **`ReportService`** рассчитывает итоги и подготавливает результат отчёта.
- **`ReportController`** вызывает сервис, добавляет результат в `Model` и возвращает имя шаблона `report`.

```text
GET /report → ReportController → ReportService → ReportRepository → БД
```

Комментарии не меняют распределение обязанностей, а перенос в произвольный утилитный класс сам по себе не задаёт нужных архитектурных границ.

**Связь с предыдущим правилом:** прямой вызов репозитория из контроллера допустим для простой операции без бизнес-логики. Здесь же SQL нужно скрыть в репозитории, а расчёт итогов — выделить в сервис. Если отдельного расчёта действительно нет, промежуточный сервис может не понадобиться.

### Разбор опроса: «Связность спрятана в файле»

**Ответ преподавателя — ②.** HTTP, SQL и расчёты в одном классе образуют антипаттерн «умный контроллер» (Smart UI). У класса несколько независимых причин меняться: HTTP-интерфейс, способ хранения данных и правила вычисления отчёта. Это связано с **S из SOLID — принципом единственной ответственности**.

Внешне класс может выглядеть аккуратно, но внутри него смешаны обязанности трёх слоёв. Сам факт, что приложение работает и тесты проходят, не доказывает удачность архитектурных границ.

**Решение — изменить границы ответственности:** выделить репозиторий с контрактом и реализацией доступа к данным, а при росте логики — сервис. Комментарии не устраняют смешение обязанностей.

**Почему вариант ④ — ловушка:** перенос всей смеси HTTP, SQL и расчётов в утилитный класс лишь меняет её местоположение. Если обязанности по-прежнему не разделены, архитектурная проблема сохраняется.

## 25. Антипаттерны: «работает, но…»

**Когда разная логика накапливается в одном месте, код теряет читаемость и его становится сложнее расширять.** Чтобы понять одну операцию, приходится разбираться в посторонних обязанностях; добавление новой возможности требует менять большой класс и учитывать множество связей. При этом объединять связанную бизнес-логику в одном ответственном за неё сервисе полезно — проблема именно в смешении разных обязанностей.

| Антипаттерн | Как проявляется | Чем мешает |
| --- | --- | --- |
| **«Умный контроллер» — Smart UI** | HTTP, SQL и расчёты реализованы в одном классе. | Несколько причин изменения; бизнес-логику трудно отделить от веб-интерфейса и хранения. |
| **Циклическая зависимость** | A зависит от B, а B — от A, напрямую или через другие компоненты. | Компоненты трудно понимать, менять и проверять по отдельности; изменения могут распространяться по циклу. |
| **God-класс — «умею всё»** | Большой класс знает о множестве частей системы и выполняет несвязанные задачи. | Теряются границы ответственности и читаемость, расширение требует вмешательства в общий узел. Число строк само по себе не определяет этот антипаттерн. |
| **Сервис-церемония** | Сервис только перенаправляет тот же вызов репозиторию без отдельной ответственности. | Добавляет файл и переход при чтении кода, не принося пользы в данной операции. |
| **Утечка слоя** | Детали SQL выходят за репозиторий, сущность хранения напрямую становится HTTP-ответом. | Соседние слои начинают зависеть от внутренних деталей друг друга; изменения хранения затрагивают внешний контракт. |

Для утечки сущности проблема проявляется, когда HTTP-контракт непреднамеренно связывается со структурой хранения. Отдельный DTO позволяет явно определить данные ответа.

**Общий вывод:** работоспособность не заменяет ясных границ. Исправление состоит в перераспределении обязанностей и зависимостей: выделить нужные компоненты, разорвать циклы, скрыть детали хранения и убрать промежуточные классы без полезной роли.

## 26. Те же зависимости в другом стеке: Python и FastAPI

**Архитектурные роли сохраняются при смене языка и фреймворка:** принять HTTP-запрос, выполнить бизнес-логику, обратиться к данным и вернуть результат.

| Java / Spring | Python / FastAPI | Роль |
| --- | --- | --- |
| Контроллер с `@Controller` или `@RestController`. | `APIRouter` и функции обработки маршрутов. | Веб-слой. |
| Сервисный класс. | Выделенная функция или класс, например `summarize(rows)`. | Бизнес-логика. |
| Репозиторий и JPA. | Код доступа к данным через ORM-сессию; при необходимости отдельный репозиторий. | Работа с хранилищем. |
| Зависимость передаётся через конструктор. | Зависимость передаётся аргументом обработчика через механизм зависимостей FastAPI. | Получение необходимых компонентов извне. |

### Упрощённый пример со слайда

```python
router = APIRouter()

@router.get("/report")
def report(db: Session):
    rows = db.query(Submission).all()
    return summarize(rows)
```

Здесь `router` задаёт веб-маршрут, `db` представляет доступ к данным, а `summarize(...)` выделяет обработку результатов в отдельную функцию.

**Оговорка к примеру:** это схема, а не полный готовый обработчик. Одна аннотация типа `db: Session` не настраивает внедрение сессии в FastAPI: зависимость нужно явно связать с поставщиком через `Depends(...)` или соответствующее объявление с `Annotated`. Кроме того, ORM-запрос пока расположен прямо в обработчике; для строгого разделения доступа к данным его выносят в отдельный компонент.

### Слои — дисциплина проектирования

Фреймворк предоставляет механизмы, но разработчик определяет границы ответственности. Сервис не обязательно должен быть классом: отдельная функция тоже может выполнять эту роль, если бизнес-логика отделена от HTTP и хранения.

В Django на слайде приведена аналогичная цепочка `view → model`; при росте бизнес-логики сервисный слой можно выделить отдельно. Django-view в этом сопоставлении выполняет роль обработчика запроса.

**Вывод слайда:** научившись прослеживать зависимости в одном стеке, можно применять тот же способ чтения к другим — искать точку входа, делегирование логики и доступ к данным.

## 27. LLM — зависимость, скрытая за интерфейсом

Вызов языковой модели — внешняя зависимость приложения, как обращение к БД. Он связан с затратами на токены, сетью, задержками и условиями доступности провайдера (SLA).

Предлагаемая схема:

```text
Controller → Service → LlmClient (интерфейс)
                           ↑ реализации
                           ├── клиент облачного провайдера
                           ├── клиент GigaChat
                           └── клиент локальной модели через LM Studio
```

### Узкий контракт и смена реализации

`LlmClient` предоставляет небольшой набор нужных приложению операций — на слайде предлагается один-два метода. Сервис зависит от этого контракта, а конкретная реализация скрывает детали вызова провайдера.

При смене облачного провайдера на GigaChat или локальную модель подменяют реализацию, сохраняя контракт. Код сервиса и контроллера не требует изменений, пока поведение нового клиента соответствует ожидаемому контракту. Это применение инверсии зависимостей.

### Тестирование без модели

В тестах `LlmClient` можно заменить заглушкой или моком с заранее заданными ответами. Так проверяется логика приложения без сети, реального расхода токенов и ожидания генерации — по тому же принципу, что контроллер тестируется с подменённым репозиторием.

### Границы определяет разработчик

LLM может сгенерировать большой класс, смешивающий разные обязанности. Разработчик отвечает за ревью и разделение кода: **«Какой это слой? Кто вызывает этот компонент? Какие зависимости ему нужны?»**

**Главная мысль:** интерфейс — точка подмены. Узкий контракт позволяет менять нижележащую реализацию, сохраняя код, который её использует.
